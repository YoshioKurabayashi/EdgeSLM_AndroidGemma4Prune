# 評価方針 ── EtoE の成功とエラーバジェット

2026-10-03 ｜ 版 0.1 ｜ 対象: 車載ルーター（対象かどうかの判定 → タスクの分類 → 引数 → 実行）の評価。実装は `app/p8_gate.py`（設計書_P8）・`app/p9_args.py`（設計書_P9）

## 1. 方針（3 つ）

1. **誤りを均等に扱わない**。「危険な誤り」と「聞き返せば回復できる誤り」を分けて数える。正答率 1 本では評価しない
2. **精度を 1 つの部品に求めない**。実行するのは、次の 3 つがそろったときだけ。どれか欠けたら聞き返す
   - BERT が「対象」と判定
   - LM ヘッドの確信度が高い
   - 引数が取り出せる
3. **閾値と規則は、評価する行を見て決めない**。閾値は validation と学習側の交差検証で決める。規則は学習側の発話から作る。評価セットは先に固定する

## 2. なぜこの方針か

- **直列の関門は誤りが積み上がる**。対象の依頼は「BERT が止めない × 棄却ヘッドが止めない × ヘッドが当てる × 引数が取れる」をすべて通る必要がある。
  全体で 99% を出すには各部品に 99.5〜99.8% が要り、ヘッドの学習だけでは届かない（現状 93〜95%）
- **並列の歯止めは見逃しが掛け算で減る**。「実行してよいか」を複数の部品に確かめさせると、個々が 8〜9 割でも誤実行は 1〜2% まで下がる（P8: 層 17 で 200 行中 21 行 → 3 行）
- **誤実行と聞き返しでは、害の大きさが違う**。「暑いな」で勝手に空調を動かすより「温度を下げますか」と聞く方が安全。聞き返しは 1 ターン増えるだけで、EtoE では成功できる
- ただし**関門を増やすほど、正しい依頼まで聞き返す割合が増える**。安全と手間の交換になるので、両方を KPI に置く

## 3. 誤りの 3 段階

|段階|中身|例|
|---|---|---|
|**重大な誤り**|操作系ツール（空調・メディア・ナビ）を、正解でないのに実行する。ツール同士の取り違えを含む|「窓を開けて」で空調を動かす／「音を止めて」で空調を止める|
|通常の誤り|実行はしないが、誤った応答になる|対象の依頼を断る／別の読むだけの機能や雑談へ流す|
|回復可能な誤り|聞き返す。1 ターン増えるが、次で正しく処理できる|対象の依頼を聞き返す／機能にない依頼を聞き返す|

読むだけの機能（状態の取得・検索・説明書・カメラ・曲の情報）の誤実行は、車の状態を変えないので通常の誤りに数える。

## 4. 数え方（真の種類 × 結果）

|真の種類|実行・雑談（正しい行き先）|聞き返し|断る|操作系を誤って実行|それ以外|
|---|---|---|---|---|---|
|対象の依頼・雑談|**正解**|回復可能（不要な聞き返し）|通常の誤り|**重大**|通常の誤り|
|機能にない依頼|—|回復可能（安全側）|**正解**|**重大**|通常の誤り|
|意図が不明|雑談として受ける = **正解**（2026-10-04 改定。それまでは通常の誤り）|**正解**|通常の誤り（応答がずれる）|**重大**|通常の誤り（読むだけの機能を実行）|

## 5. KPI と目標

|KPI|定義|検証の目標（いま）|最終の目標（仮）|
|---|---|---|---|
|**EtoE の成功**|正解 ＋ 回復可能 の割合|**95% 以上**|99% 以上|
|**重大な誤り**|操作系の誤実行の割合|**1% 以下**|0.05〜0.1% 以下|
|**不要な聞き返し**|対象の依頼・雑談を聞き返した割合|**5% 以下**|1% 程度|
|通常の誤り|上のどれでもない誤りの割合|3% 以下|0.2〜0.3% 以下|
|1 回目で正しく処理（参考）|正解だけの割合|—|—|

- 検証の目標は、いまの評価セットの行数（200 行）で意味のある幅に置いた
- 最終の目標は仮置き。実際の利用の配分（対象・対象外・意図が不明の割合）をログから入れて決め直す
- **この 4 つは、どの機能を実行したかまでを見る。渡した引数の値は見ていない**（P21 で、値の違う実行が操作系の 2 割ほどあると分かった。8 節・9 節）
- **値まで見た KPI（P22 から。利用者が決めた・2026-10-07）**: 正しいツールを実行したが、値が正解と違う行を「違う値での実行」として数え、EtoE の成功から引き、重大な誤りに足す（操作系の誤実行なので）。引数の段だけを測るときは、行を **合っている／聞き返す／違う値で実行** の 3 つに分ける。聞き返すのは安全な外し方で、不要な聞き返しに数える。目安: 操作系の対象で、違う値での実行 3% 前後まで

## 6. 実行の流れ（評価もこの順で通す）

EdgeSLM_MultiHead_Multi の `Dispatcher._handle` と同じ順。

```
発話 → BERT が断る（確率が高い）                     → 断る
     → LM ヘッドで分類 → 規則 → 棄却の得点 → 確信度   → 欠けたら聞き返す
     → 引数を決める → 検査（schema・値域・ポリシー）   → 欠けたら聞き返す（ポリシー違反は断る）
     → BERT のフラグ（確率が中間）かつ操作系          → 聞き返す
     → 実行
```

役の分け方: 対象かどうかは BERT、タスクの分類と意図が不明は LM ヘッド（＋規則）、最後の歯止めは引数と検査。

「規則」の中身（P21 の時点。上から順に試し、どれかが決めたら次は試さない）: EdgeSLM_MultiHead_Multi の 4 つの規則 → S1 言い直し・S2 取り消し・S3 言いよどみ（P13）→ S4 別の操作系ツールの語がある（P14）→ 指示語でない言い回しの例外（P17）→ **S5 実行しようとする操作系ツールの語が 1 つも無い（P19）** → **P21 の直し（位置の「前の」・動詞に付いた「直し」「忘れて」を指示語・取り消しとして拾わない／「〜して、あ、待って」「〜なんだけど」を拾う）**。S1〜S5 と P21 の直しは本プロジェクトの補いの層で、履歴の無い発話にだけ効く。

## 7. 測るときの決まり

- **行数**: 「誤りは p% 以下」を言い切るには、誤りゼロでも 3 ÷ p 行が要る（1% なら 300 行、0.1% なら 3,000 行、0.05% なら 6,000 行）。
  いまの 200 行では、重大な誤り 1% は 2 行で、合否が 1 行で変わる。**率と一緒に件数を出す**
- **評価の文**: 学習の文と同じ人が書くと良く出る。別の人の文・実際の発話を入れる（`data/challenge_v2/user_rows.tsv`）
- **ばらつき**: ヘッドの seed 3 つ・BERT の seed 2 つの平均と最小〜最大を出す。1 つの seed の差をモデルの差と読まない
- **実際に使うモデルで確かめる**: 交差検証の数字は、5 つに分けて学習した別のモデルのもの。全体で学習したモデル（実際に使うもの）は、学習側の test で確かめてから使う（P18: seed 1 つだけ、対象の依頼へのフラグが 3 倍だった）
- **閾値の決まりは、学習し直すたびに「実際に止める量」を見直す**: 同じ「validation の 2%」でも、ヘッドを学習し直すと、評価セットで止める量が半分になった（P18）
- **部品を 1 つずつ足して測る**: どの部品が何を減らし、何を増やしたかを分ける（ヘッドだけ → ＋規則 → ＋引数の検査 → ＋BERT）
- **どの段で止まったかを出す**: 不要な聞き返しの原因が、分類なのか引数なのかを分ける
- **規則と引数を直したら、これまでの行すべてで 1 行ずつ比べる**: 止まらなくなった「機能にない依頼・意図が不明」の行が 0、新しく止まる対象の行が 0 を、通す条件にする（P21: 最初の案は 3 文を通してしまった）
- **見ていない行で測る → 直す → また別の見ていない行で測る**: 見ながら直した行では、何を直しても 100% になる。直しが効いたかは、直しを決めた後に書いた行でしか分からない。2 回測ると、上がり方（次も上がりそうか）が見える（P22・P23）
- **形の違う文を、形ごとに分けて入れる**: 理由が前・理由が後ろ・ていねい・くだけた・条件つき・2 つのこと・長い文、のように形を決めて同じ数ずつ書く。どの形で外すかが見える（P22）
- **測るものを md5 で止めておく**: 評価セットと、直したソースの md5 を、測る前に設計書に書く。判定のときに同じ値かを出す（P21）
