## 1. 目的

これまでの検証（P1〜P23）は、端末で `h` を集め、判定は PC で出していた。**発話 1 つを入れると、最終の判定（実行／雑談／聞き返す／断る）までを、スマホの中だけで出すアプリ**を作る。

- 層の数（前半 17 層＝軽量版／前半 26 層）を、画面で切り替えられる
- BERT（機能にない依頼を断る）も端末で動かす
- 各段の値（BERT の確率・行き先と確信度・当たった規則・棄却の得点・引数・検査）と、各段の時間を出す
- 操作は模擬（「この機能をこの引数で呼ぶ」と表示するだけ）。聞き返した後の 2 回目のやり取りは入れない

**既存のものには影響させない**。別のアプリ（新しい applicationId）として作り、既存のアプリのソース・置き場には書き込まない。学習はしない。

## 3. 判定の流れ（`app/p24_decide.py`）

評価の流れ（`p8_gate.run`）は、評価セットをまとめて流す形で、発話 1 つを渡す入口が無かった。同じ順番を 1 発話ずつ返す関数 `decide` を書いた。**アプリは、これと同じ結果を返すように作る**。

```
BERT の確率 ≥ 0.9943（断る閾値）            → 断る
ヘッドの 1 位 → 規則（聞き返すと決めたら）  → 聞き返す
棄却の得点 ≥ 閾値                           → 聞き返す
確信度 < τ（雑談・操作系・読むだけ で別）    → 聞き返す
雑談なら: BERT ≥ 0.5 → 聞き返す／それ以外   → 雑談
引数が足りない                              → 聞き返す
検査（型・範囲・走行状態の決まり）が通らない → 聞き返す（必須が無い）／断る
BERT ≥ 0.5（フラグ）                        → 聞き返す
それ以外                                    → 実行
```

`decide` が評価の流れと同じかは、`app/p24_fixtures.py` が評価セット v6・v5 × 層 17・26 で、KPI・止めた行・重大な誤りの行を突き合わせる（`results/P24/decide_check.md`）。

## 4. 端末に載せる部品と、PC と同じかの確かめ

規則と引数の取り出しは Python で書いてある。端末で Python は動かさず、**Java に書き直した**（`android_app_router/app/src/main/java/org/edgeslm/router/`）。書き直しで結果が変わっていないかを、PC の結果と 1 行ずつ突き合わせる（`tools/p24_java/`）。

|部品|アプリ（Java）|元（Python）|突き合わせ|
|---|---|---|---|
|規則|`Rules.java`|EdgeSLM_MultiHead_Multi の `dispatch/rules.py` → `p13`・`p14`・`p17`・`p19`・`p21_rules`|`ParityTest`: 発話 5,047 × 判定 9 通り = 45,423 行|
|引数の取り出し|`Args.java`|`dispatch/arguments.py` → `p9`・`p17`・`p21`・`p22`・`p23_arguments`|`ParityTest`: 発話 5,047 × 機能 8 つ = 40,376 行（そろうか・値）|
|検査|`Policy.java`|`dispatch/policy.py`・`configs/tools.json`・`configs/policy.yaml`|同上（停車中・走行中の 2 通り）|
|判定の流れ|`Flow.java`|`p24_decide.decide`|`ParityTest`: 評価セット v6 の 600 行 × 層 17・26|
|ヘッド|`Head.java`|`g3_headlib.numpy_head`（既存の画面の `HeadModel.kt` と同じ式）|`HeadTest`: 評価セット v6 の端末の `h` 600 行 × 層 17・26（確率の差・`h` からの判定）|
|BERT の入力作り|`BertJa.java`|`BertJapaneseTokenizer`（MeCab ＋ WordPiece）|`TokTest`: 発話 5,047 ＋形の違う文 25（ID 列・単語の分け方）|
|表示の言葉|`Say.java`|—（表示だけ。判定には関わらない）|—|
|Python と Java の違いを埋める道具|`Py.java`|—|上の突き合わせで確かめる|

発話は、学習の履歴なしの行・評価セット v1〜v6・`arg_eval_v1`・`v2` のすべて（重なりを除いて 5,047）。正解の表は `work/p24/fixtures/`（`p24_fixtures.py` が作る）。

書き直しで気をつけた所:

- Python の `\s` は全角の空白も拾う。Java は ASCII だけ、Android は Unicode、と違うので、文字クラスを明示した（`Py.WS`）
- Python の `strip()`・幅 0 の一致での `re.split`・関数を渡す `re.sub` は、同じ動きの関数を `Py.java` に書いた
- 辞書の語を見る順番（Python の dict の順・長い順に並べた助詞）を、同じ順で配列にした
- 引数の数は、温度は実数（`24.0`）、風量・音量は整数。Python と同じ書き方の文字列（`Args.canon`）にして比べる
- 使うのは Java 8 の範囲の機能だけ（Android API 26 で動くもの。PC の確かめは `javac --release 8` でコンパイルする）

**なぜ Kotlin ではなく Java か**: アプリの既存の部分は Kotlin だが、足した部分は Java にした。Java なら、Android の SDK（`android.jar`）と ONNX Runtime のクラスを相手に、ビルドの前にコンパイルを確かめられる。判定の部品は、PC の `java` でそのまま動かして突き合わせられる。Kotlin の部品（`NativeBridge`・`Gemma4Tokenizer`・`JsonInject`）は、そのまま呼ぶ（`tools/p24_java/stubs/` は、コンパイルの確かめのときに Kotlin の部品の代わりに置いた形だけのもの。アプリには入れない）。

## 5. BERT を端末で動かす

### 5.1 分かち書き（`BertJa.java`）

いまの日本語 BERT は、1) NFKC でそろえる 2) MeCab（辞書は unidic-lite）で単語に分ける 3) 単語を WordPiece で分ける。端末で同じ分け方ができないと、PC と同じ確率が出ない（システム構成案 6 節の「最初に確かめること」）。

**MeCab の単語分けを Java に書いた**（システム構成案の案 A）。辞書は unidic-lite の中身をそのまま使う。

|もの|元|端末|
|---|---|---|
|見出しの表・単語の表|`sys.dic`（179MiB）の先頭 28MiB|`sys_lex.bin`（切り出しただけ。品詞などの文字列 151MiB は使わないので送らない）|
|つながりのコスト|`matrix.bin`（68MiB）|そのまま|
|文字の種類・未知語|`char.bin`・`unk.dic`|そのまま|
|語彙|`vocab.txt`（32,768 語）|そのまま|

書いた中身は、MeCab の `Tokenizer::lookup`（辞書引き・空白を飛ばす・未知語をまとめる）と `Viterbi`（いちばん安い道）。候補を並べる順番と、同点のときの選び方も同じにした。辞書はファイルをメモリに対応づけて読む（Java のヒープを使わない）。

ほかの案を採らなかった理由: MeCab の本体（C++）を組み込む・Python を端末で動かす（Chaquopy）は、どちらも新しい依存の取得が要る。文字単位の BERT に替える（案 B）は、学習と評価のやり直しになる。

### 5.2 モデル（`BertScorer.java`）

`work/p20/bert_F/bert_s0`（P20 で保存）を ONNX にする（`app/p24_assets.py bert`。float32 のまま・約 424MiB・1 つのファイル）。端末では、アプリに入っている ONNX Runtime 1.27 の Java の口（`ai.onnxruntime`）で、**CPU で**動かす（NPU は Gemma 4 のグラフが使う）。新しい依存は足していない（AAR は元のアプリと同じもの）。

1 文ずつ流すので、詰め物（padding）は無い。入力は最大 64 トークン（PC と同じ）。

### 5.3 確かめ

|確かめ|どこで|合格の目安|
|---|---|---|
|ID 列が PC と同じか|PC（`TokTest`）・端末（`check`）|すべて同じ|
|ONNX の確率が torch と同じか|PC（`p24_assets.py bert`）|差 1e-3 未満（超えたら止める）|
|ONNX の確率が、P21 で保存した確率（GPU・まとめて計算）と同じか|PC（同上）|閾値（0.9943・0.5）をまたぐ行が無い|
|端末の確率が PC と同じか|端末（`check`）|同上|

## 7. 画面（`RouterActivity.java`）

- 1 回の判定: Gemma 4 の入力作り → NPU（Runner の `classify_prefill`。既存の機能）→ ヘッド。並行して、BERT の入力作り → BERT（CPU）。そろったら `Flow.decide`
- 層の切り替え: グラフは初めて選んだときに開き、開いたままにする（2 つで約 1,346MiB。1 プロセスの NPU の上限 約 1,710MiB の内）。2 つ目が開けなければ、先に開いていた方を閉じて開き直す
- 車の状態（走行中）は、ヘッドの入力の文（`[状態] 走行:moving`）と、検査（走行中は目的地を設定できない・音量 30 以上にできない）に効く
- 発話が長くて Gemma 4 のトークンが 64 個を超えたら、判定せずにそう表示する（グラフが 1 回で読めるのは 64 個まで）
- 自動実行（adb の引数）: `--es prompts "発話1|26:|発話2"`（順に判定。`26:` は層の切り替え）・`--es eval "17,26"`（確かめ用の行を全部流す）

## 11. 結果（2026-10-05。くわしくは `results/P24_20261005_app.md`）

- ビルドは 1 回目で通った。2 つのグラフは同時に開けた
- **端末の判定は、評価セット v6 の 600 行 × 層 17・26 のすべてで PC と同じ**（結果・止めた段・機能・引数）。Gemma の入力・BERT の入力も全部同じ。BERT の確率の差は 1.6e-06、ヘッドの確信度の差は 2e-15
- 端末なしの突き合わせ（規則 45,423・引数と検査 40,376・流れ 1,200・ヘッド 1,200・BERT の入力作り 5,072 行）は、すべて食い違い 0。BERT の ONNX は torch と差 5.4e-06
- 1 回の判定（中央値）: 層 17 で 130 ms・層 26 で 164 ms。BERT（CPU）は 51〜57 ms、規則・引数・検査は 0.2 ms、BERT の分かち書きは 0.3〜0.4 ms
- 合計は、部品の長い方より 75〜90 ms 長い。Runner の `classify_prefill` が 1 回ごとに表（約 48MiB）を読み直している分と、`h` を JSON で受け渡している分とみている（測っていない）。**縮めるなら、ここ**（表を開いたままにする。C++ の Runner の変更が要る）
