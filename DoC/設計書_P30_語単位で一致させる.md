# 設計書 P30: 機能の定義で絞るとき、語を単語の切れ目で一致させる

版 0.1（2026-10-13・当たりを付けた結果まで）

対象のソース: `app/p30_words.py`・`app/p30_scope.py`・`app/p30_check.py`・`tools/p30_java/WordsDump.java`・`data/p30_words/words.tsv`・`results/P30/check.md`・`results/P30_20261013_words.md`

## 1. 目的

P29 の「機能の定義で絞る」（`p29_scope`）は、語の一覧を発話の**部分文字列**で探した。そのため「宿題」の「宿」（周辺の検索）・「スキー場」の「キー」（説明書）・「名前」の「前」（カメラ）・「屋根」の「屋」（周辺の検索）が根拠になった。
発話を単語に分け、**語が単語の切れ目に合うときだけ**根拠にすると、この型の誤りが減るかを確かめる（利用者の選択・2026-10-13）。

## 2. 変えるもの・変えないもの

|部品|P30|
|---|---|
|語の一致|部分文字列 → 単語の切れ目に合わせた一致|
|語の一覧|P29 のまま。単語の一致にして落ちた**対象の**言い方 4 語（真後ろ・タコメーター・後輪・前輪）を足した|
|単語の分け方|端末の BERT の入力作りと同じ（NFKC ＋ MeCab ＋ unidic-lite）|
|ヘッド・BERT・規則・引数（P26）・閾値|変えない（ヘッドは P28 の 1,656 行）|

## 3. 単語の分け方（`app/p30_words.py`）

- アプリはすでに、BERT の入力を作るために MeCab と同じ分け方を Java で持っている（`BertJa.java`・P24。PC の `BertJapaneseTokenizer` と 5,072 行すべてで同じ）。**同じ分け方を使えば、アプリでも新しい依存なしにそのまま使える**（`BertJa.words()`）
- PC で fugashi が無い環境（VM の python3）では、端末と同じ `BertJa.java` で分けた表 `data/p30_words/words.tsv` を引く（`tools/p30_java/WordsDump.java` で作った。評価セット v6〜v8 と学習 1,656 行の 3,438 文）。fugashi がある環境では、その場で同じやり方で分ける
- 表は、P24 の PC の分け方の表と重なる 2,037 行で食い違い 0

一致の決まり（`aligned`）:

|語|決まり|例|
|---|---|---|
|2 文字以上|単語の始まりに合えばよい（語幹・複合語の頭）|「走れる」の「走れ」・「前方」|
|1 文字の向き・曲の語（前・後・左・右・横・曲・歌）|単語の始まりに合えばよい|「右側」「左前」「曲名」「歌って」|
|1 文字のそれ以外（宿・屋・店・鍵・窓・駅・局 など）|単語そのものと同じときだけ|「ラーメン 屋」は通る・「屋根」「宿題」は通らない|

## 5. 結果（`results/P30_20261013_words.md`）

- 部分一致の誤りは、機能にない依頼・意図が不明の行で 19 行なくなった（「屋根」の「屋」5 行・「〜リア」の「リア」3 行・「名前」の「前」3 行・「宿題」「スキー」「モール」など）
- **流れの KPI はほとんど変わらない**（v8・層 26 で EtoE 0.956 → 0.954・通常の誤り 3.7% → 3.8%・不要な聞き返し 6.5% → 6.3%。v6・v7 は同じ）。直した 19 行は、流れの中では結果を変えなかった（その読み出しの機能に回らなかったか、別の段で止まっていた）
- 変わった行は 1 行だけ: 足した語「後輪」で、「後輪の左側は何キロパスカル」が説明書として通るようになった（通常の誤りが 1 行増えた）
- 残る型: 単語として正しく一致するが意味が違う（「右折」の「右」・「前の持ち主」の「前」・「途中経過」の「途中」）、対象と同じ語を使う依頼（「レストランの評判」「駐車場の値段」）

## 6. 判断の材料

- 単語の一致は、**流れの数字は変えないが、偶然の一致を減らす**。評価セットに無い言い方（「屋根の〜」「〜リア〜」）で、別の機能に回ったときの抜け道を減らす
- アプリでは、BERT の入力作りの単語分けをそのまま使えるので、実装の負担が小さい
- 語を足すと、足した語の抜け道もできる（「後輪」→ 説明書）。語の一覧は、機能ごとに分けて持つ（車両の状態の語を説明書に使わない）方がよい
