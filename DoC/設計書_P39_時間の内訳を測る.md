# 設計書 ── P39: 判定 1 回の時間を、部品ごとに分けて測る

2026-10-15 ｜ 版 0.1 ｜ 対象: `android_app_router3/`（判定デモ v3・測定 `org.edgeslm.gemma4router3`）・`app/p39_latency.py`・`scripts/run_p39.ps1`・`scripts/p39_build_app.ps1`

## 1. 目的

アプリ v2 の判定 1 回（層 17 で中央値 144ms・層 26 で 173ms。P37）のうち、記録している部品（Gemma のトークン化・表引き・NPU・ヘッド・規則）を足しても **約 89ms（層 17）・約 99ms（層 26）が説明できない**（P37 の 600 行から計算）。
また BERT は NPU と並行に動いているので、「BERT がどれだけ全体を延ばしているか」も今の記録では分からない。

そこで、次の部品の時間を**別々に**測る:

- BERT（トークン化・推論。並行のときに待った分と、単独のときの全部）
- Gemma の層（NPU の Run）。層 17・26・**35**（35 層は未測定だった「判定全体」を実測する）
- 埋め込み・PLE の表引き（CPU）、RoPE・マスク
- 毎回の準備（describe・表を開く・スケールを読む・入力の器）
- 受け渡し（job の JSON・JNI・結果の JSON・h を float にする）
- NPU の中（QNN の計測で、入口の PLE の投影・層ごと・最後の正規化に分けられるかを試す）

## 2. 既存のものに影響させない

- アプリ v2（`android_app_router2/`）の**複製** `android_app_router3/` を作り、時計と測定の流し方だけを足した。applicationId `org.edgeslm.gemma4router3`・表示名「Gemma4 判定デモ v3 測定」。**v2 のソースとアプリ・その置き場は変えない**
- 判定の部品（Java の Flow・規則・引数・ヘッド・BERT）と C++ の計算は v2 と同じ。C++ は表引きを「埋め込み」と「PLE」の 2 つのループに分けたが、書く値は同じ
- 端末の資材は、v2・お試しアプリの置き場にある同じものを、**端末の中で写す**（そちらは読むだけ）。v3 の置き場に約 4.3GB 増える
- 書き込むのは `work/p39/`・`results/P39/`・端末の v3 の置き場だけ

## 3. 足した時計

### C++（`runner/job.cpp` の classify_prefill → 結果の `timing`）

|名前|中身|
|---|---|
|`pre_describe_versions`|run_job の頭で毎回やる describe・versions|
|`describe`|classify_prefill の頭でもう 1 回やる describe|
|`embed_open`|埋め込みの表（2bit・96MiB）を mmap で開き、スケール（1MiB）を読んで写す|
|`ple_open`|PLE の表（4bit・1,120MiB）を mmap で開き、スケール（**35MiB**）を読んで写す|
|`alloc`|入力の器（ple_tok は 64×35×256×4B = 2.3MB ほか）|
|`rope`|位置の表 4 つ（計 12MiB）を読み、先頭 64 行を写す|
|`mask`|因果のマスク（64×64）|
|`fill_embed`・`fill_ple`|表引き（T=64 行。詰め物の行も含む。PLE は 35 層ぶん）|
|`run_ort`|ORT の Run（NPU）|
|`run_wall`|Run の前後（入力の包み・出力 h [1,64,1536] の写しを含む）|
|`h_mean`・`h_json`|h の平均・最後と平均を JSON の配列にする|

### JNI（`edgeslm_jni.cpp` → 結果の `jni_timing`）

`get_string`（Java の文字列を受け取る）・`parse_job`（job の JSON を読む）・`run_job`（上の全部）。結果を文字列にする（dump）・Java へ返す時間は、Java の `jni_ms` から引いて求める。

### Java（`RouterActivity.compute` → 記録の各列）

`job_build_ms`（job の JSON を作る。`JsonInject.addRuntimePaths` の読み直しを含む）・`jni_ms`（nativeRunJob 全体）・`parse_ms`（結果の JSON を読む）・`floats_ms`（h を float にする）・`bert_wait_ms`（並行のとき、ヘッドの後に BERT を待った時間）・`gemma_path_ms`・`bert_path_ms`（serial のとき）。

## 4. 流し方（`--es bench`）

- 確かめ用の行（評価セット v11）の先頭 **300 行**を、層 17 → 26 → 35 の順に流す。層を変えるときは、ほかの層を閉じてから開く（35 層は 1 つで約 1,273MiB）
- 層ごとに **par**（v2 と同じ。BERT を NPU と並行）→ **serial**（BERT を先に単独で動かしてから Gemma。それぞれ単独の時間）。各モードの前に 10 行を流して捨てる（準備運転）
- 最後に、層ごとに **QNN の計測**（ORT の QNN EP の `profiling_level=detailed`・`profiling_file_path`）を付けて開き直し、30 行を流す。事前に変換したグラフ（EPContext）なので、細かい内訳が出ないかもしれない。開けなければ飛ばす（そのときは 7 節の代わりの方法）
- 35 層は**ヘッドが無いので層 26 のヘッドを借りる**（h の大きさは同じ 1,536）。**判定は見ない。時間だけ**
- 結果: `out/bench_L<n>_<mode>.jsonl`・`out/qnnprof_L<n>.csv|.jsonl`。終わるとログ `router_bench done`

## 5. 手順（利用者が PowerShell で）

```powershell
.\scripts\run_p39.ps1                   # ビルド → 設定 → 送る → 測る → まとめ
.\scripts\run_p39.ps1 -Stage bench -Layers "17,26" -Rows 100 -QnnProf off   # 短く試す
```

まとめ（`app/p39_latency.py report`）は `results/P39/latency.md`・`latency.json` に、グループごと・部品ごとの中央値と p90、足し合わせの残り（測っていない分）、PC と同じ判定か（層 17・26）、QNN の計測のまとめを書く。

## 6. 予想（測る前に書いておく）

コードを読んだうえでの予想。外れたら外れたと書く。

1. **説明できなかった約 89ms の大半は、毎回の準備と受け渡し**。特に PLE のスケール 35MiB と RoPE の表 12MiB を毎回読んで写す分、結果の JSON（describe・versions・h 3,072 個）を文字列にして Java で読み直す分が大きい
2. BERT は単独で 50〜60ms（層 17 では Gemma 側とほぼ同じ長さ）。並行のときに待つのは数 ms
3. 表引き（CPU）は埋め込み 1〜2ms・PLE 3〜5ms。RoPE の計算は無い（写すだけ）
4. NPU は層 17 で 45ms 前後・層 26 で 65ms 前後・層 35 で 88ms 前後（P2 と同じ）。判定全体は層 35 で 180ms 前後
5. 35 層は BERT と一緒に開けるかが際どい。開けなければ、35 層だけ結果が無い（その旨を書く）

## 7. QNN の計測で内訳が出なかったときの代わり

入口のかたまり（PLE の投影・35 層ぶん）だけのグラフを PC で変換して端末で測り、層のグラフとの差から「入口」と「層」の時間を分ける（変換に 30〜60 分。このときだけ別に用意する）。

## 8. この先（結果を見てから決める）

準備を 1 回だけにし（表・スケール・RoPE・マスク・器を開いたときに作って持っておく）、h を JSON ではなく配列で受け渡す版を作り、どれだけ速くなるかを測る（v3 の複製で）。

## 9. 結果（2026-10-15）

[results/P39_20261015_latency.md](../results/P39_20261015_latency.md)。部品を足すと全体と 0.1ms 以内で合った。層 17・26 は PC と同じ判定 300/300。

- 層 17 の判定 143ms（par）のうち、NPU 43ms・**PLE のスケールを毎回読む 51ms**・片付けと結果の写し 14ms（推定）・RoPE の表を読む 7ms・JSON 約 10ms
- BERT は並行のとき待ち 0ms（全体を延ばしていない）。単独では 33〜89ms と、測った順に延びた（温度の可能性。未確認）
- QNN の計測（detailed）はノードごとに出た（7 節の代わりの方法は要らない）。入口（35 層ぶんの PLE の投影など）は全体の 2〜3%
- 予想との比べは結果の 7 節。次は 8 節（準備を 1 回だけにする版）
