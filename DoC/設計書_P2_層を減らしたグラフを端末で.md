# 設計書 ── P2: 層を減らしたグラフを端末で（層 17・層 26）

2026-10-01 ｜ 版 0.1 ｜ 対象: `app/p2_build.py`・`app/p2_device.py`・`app/p2_heads.py`・`app/pipeline/`（写し）・`scripts/run_p2.ps1`・`scripts/p2_build_app.ps1`・`scripts/build_context.sh`・`scripts/qairt_converter_int4.py`（写し）・`android_app_prune/`

## 1. 目的

P1（PC）で、層を減らしても分類の精度が保てる候補が 2 つ見つかった（`results/P1_20261001_layers_errors.md`）。

|候補|PC での正解率（35 層との差）|誤実行|性格|
|---|---|---|---|
|層 26（層 0〜25）|0.857（+0.009）|0|安全側。削減 25%|
|層 17（層 0〜16）|0.844（−0.005）|2（棄却の閾値で止められる見込み）|攻め側。削減 51%|

P2 では両方を**端末の NPU 用のグラフ**にして、35 層（改善版 B）と同じ端末・同じ回に流し、**速さ・グラフの大きさ・端末の `h` で学習したヘッドの精度**を比べる。

## 2. 既存のものに影響させない

- 書き込むのは本プロジェクトの `work/`・`results/` と、お試し用の**新しいアプリ**（`org.edgeslm.gemma4prune`）の端末の置き場だけ
- EdgeSLM_AndroidGemma4Head の改善版 B の量子化済みのかたまり（A・B）・較正のデータ・35 層のグラフは**読むだけ**
- 変換の道具（`app/pipeline/`・`scripts/build_context.sh`・`qairt_converter_int4.py`）は本プロジェクトへ**写した**（写した元の md5 は引き継ぎ一覧）。
  写しの `gemma4_common.py` は置き場（`ROOT`）がファイルの場所から決まるので、書き込み先は自動で本プロジェクトの `work/` になる
- 既存のアプリ（gemma4head・gemma4headfast・gemma4headgen）とその置き場には触れない。端末の作業の前に止めるだけ（RAM の都合）

## 3. グラフの作り方（`app/p2_build.py`）

改善版 B（35 層・T=64・KV なし・出力 `h`）と同じ作り方で、後ろの層を外し、残した最後の層の直後に最後の正規化を付ける。

|グラフ|かたまり|新しく作るもの|
|---|---|---|
|`p2_L17`|A（入口＋層 0〜8、改善版 B のもの）＋ **N17（層 9〜16＋最後の正規化）**|N17|
|`p2_L26`|A ＋ B（層 9〜17、改善版 B のもの）＋ **N26（層 18〜25＋最後の正規化）**|N26|

- PLE の入力 `ple_tok` は 35 層ぶんのまま（入口のかたまり A を使い回すため）。端末の PLE の表も 35 層ぶんのものを使う。
  表は CPU 側で読むだけで NPU のメモリには載らないので、端末での差はグラフの大きさと NPU の時間に出る
- 層 15・16 は層 13・14 の K/V を使い回す。N17 は 13・14 を自分の中で作る。N26 は B が作った K/V を入力で受ける（`shared_k_13` など）
- 較正のデータは改善版 B の較正（かたまりごとの入力、SRQ あり）をそのまま使う（N17 の入力 ＝ B の入力、N26 の入力 ＝ C の入力）
- 量子化は改善版 B と同じ（a16w8_rhs8 → QAT の値の書き込み → 量子化されない入力に作る側と同じ目盛りの Q/DQ → act×act の右辺を 8bit）
- `ortcheck`: 繋いだ QDQ を PC の ORT で 8 行流し、`h` を P1 の HF の値（同じ層の数・SRQ あり）と比べる。**参考**（改善版 B の 35 層は最後 21%）。有限でなければ止める
- 変換: QAIRT（`QAIRT_INT4_PATCH=1`）→ EPContext。大きさの見込み: 層 17 で約 0.5GB、層 26 で約 0.9GB（35 層は 1,273MiB）

## 4. 端末（`app/p2_device.py`・`android_app_prune/`）

- アプリ: 改善版 B のアプリ（`android_app_fast/`）を複製し、`settings.gradle`・`app/build.gradle`（applicationId `org.edgeslm.gemma4prune`）・
  `AndroidManifest.xml`（表示名「Gemma4 層削減お試し」）だけ変えた。Runner の `classify_prefill` を使う（`job.cpp` は変更なし）。分類の画面はこの版では使わない
- `deploy`: 表（EdgeSLM_AndroidGemma4 の `work/tables`）・トークナイザ・3 つのグラフ（層 17・26・35）を送る。35 層は改善版 B のもの（読むだけ）
- `speed`: 16 行を 3 つのグラフで流す（グラフごとにアプリを止めて開き直す）。NPU・準備・合計の中央値と、グラフの大きさ
- `collect`: 714 行を 3 つのグラフで流し、`h`（最後・全位置の平均）を `work/p2/L<n>/device/features` へ。同じ層の数の PC の HF（P1）との差も記録

## 5. ヘッド（`app/p2_heads.py`）

端末の `h` で、EdgeSLM_MultiHead_Multi の train・evaluate・crossval をそのまま回す（G1・B4・C3・P1 と同じ）。
同じ層の数の PC の HF（P1）と並べ、**端末の量子化で、層を減らした効果が消えないか**を見る。

## 6. 判断の目安

- 層 17 の端末の精度が 35 層の端末（改善版 B4: 交差検証 0.859）と同じくらいで、NPU が半分近くなら、分類専用の作りとして十分使える
- 層 17 の誤実行が端末でも「行く、やめる」だけなら、棄却の閾値の基準の見直しで対応できる
- 層 26 は安全側の基準。層 17 の結果が悪いときの代わり
