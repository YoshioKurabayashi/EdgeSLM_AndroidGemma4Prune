# 設計書 P29: 対象の機能以外をはじく（機能にない依頼を列挙しない）

版 0.1（2026-10-10・当たりを付けた結果まで）

対象のソース: `app/p29_scope.py`・`app/p29_check.py`・`results/P29/check.md`・`results/P29_20261010_scope.md`

## 1. 目的

P28（評価セット v8）で、「〜を教えて・調べて」の形の機能にない依頼（天気・交通・暦など）を BERT がほとんど止められず（フラグ 0.14）、読み出しの機能で実行して通常の誤りが 11% になった。

BERT は**機能にない依頼の例**で学習している（297 行。問い合わせの形は 2 行だけ）。例に無い形は止められない。機能にない依頼は無数にあるので、例を足していくのは評価セットに合わせるだけになる（**利用者の指摘・2026-10-10**）。

ここでは逆に、**対象の 8 機能（閉じた集合）で説明がつく依頼だけを通す**やり方を試す。

## 2. 決まり（利用者と合意・2026-10-10）

- 機能にない依頼の行は、**評価にだけ使う**。学習・閾値・語の一覧の調整には使わない
- 対象の側（8 機能の言い方）は閉じているので、対象の行を見て語を足すのはよい。ただし、そのときは対象の行での数字が甘くなるので、合否は新しい評価セットで測る

## 3. やり方 1: 機能の定義で絞る（`app/p29_scope.py`）

いまの引数の処理は、当てはまる語が無いと既定値で埋めて実行する（「外のPM2.5の値を教えて」→ 車両の状態「全体」・「雨雲レーダーを表示して」→ カメラ「後ろ」・「歌った点数を出して」→ 曲の情報「再生中の曲」）。
読み出しの 5 機能を、**機能の定義（`tools.json` の項目）から書いた語の一覧**で絞る。発話にその機能で説明がつく語が無ければ、`missing = ["scope"]` として返す（流れは聞き返す）。

|機能|定義|根拠とみなす語|
|---|---|---|
|車両の状態|item = 燃料・航続距離・走行距離・空気圧・ドア・バッテリー・全体|項目の語・状態の語（異常・不具合・警告など）・車の部品の語|
|カメラ|view = 前・後ろ・左・右・周囲・車内|向きの語・カメラ／映像／モニター|
|曲の情報|item = 再生中の曲・アーティスト・アルバム・音源・次の曲|曲・歌・アーティスト・アルバム・番組・局など|
|説明書を調べる|自由な検索語（車の取扱説明書）|**車の部品・装置・操作の語**（「使い方」「方法」だけでは足りない）|
|周辺の施設を探す|自由な検索語（施設）|施設・店の種類の語、または「近く・この辺・周辺」|

- 語の一覧は、機能の定義と項目の意味から書いた。機能にない依頼の行は見ていない
- 書いた後、v6〜v8 の**対象の**読み出しの行で説明がつかなかった 13 行を見て、対象の言い方 11 語を足し、状態の語だけでも通すことにした（対象の側なので決まりの内。ただし v6〜v8 の対象の行での数字は甘い）
- 操作の 3 機能（空調・メディア・ナビ）は変えない（P25・P26 の歯止めのまま）

## 4. やり方 2: 対象の依頼との近さ（h）

ヘッドが使う h（最後のトークン・平均）で、学習の対象の行（train）からの近さを測る（近い 5 行との cos 距離・マハラノビス距離（主成分 64））。閾値は対象の行（validation）を 2%・5% 誤ってはじく値。機能にない依頼は使わない。

## 5. 当たりの付け方（`app/p29_check.py`）

端末なし・学習なし。端末で集めた h（v6・v7・v8）と、P28 の BERT の確率を使う。ヘッド 1,656 行・1,584 行 × 引数 P26・P29 で、流れの KPI（値まで見たもの）・種類ごとの扱い・P26 → P29 で変わった行を出す。やり方 2 は、はじいた割合だけ出す。

**v6〜v8 はどれも直す用。ここの数字は当たりで、合否ではない**（v8 の弱点を見てから考えたやり方なので）。

    python -m app.p29_check        # results/P29/check.md・check.json

## 6. 結果（`results/P29_20261010_scope.md`）

- やり方 1 は大きく効いた。v8 の通常の誤り 11.4〜11.9% → 3.6〜3.7%・値まで見た EtoE 0.874〜0.879 → 0.956〜0.958。v7・v6 でも通常の誤りが半分ほどに。代わりに不要な聞き返しが 0.2〜1.1 ポイント増える（ほとんどは、ヘッドが別の読み出しの機能を選んだ行＝もとは通常の誤り）
- やり方 2 はほとんど効かない（v8 の unseen でも 2% の閾値で 9〜28%）。h は文の形（「〜して」「〜教えて」）を強く表していて、対象と機能にない依頼の区別には向かない
- 残る弱点: 語の部分一致（「宿題」の「宿」・「スキー」の「キー」・「名前」の「前」）と、対象と同じ語を使う依頼（「レストランの評判」「駐車場の値段」「タイヤの温度」）

## 7. 次に決めること

- やり方 1 を本採用の候補にするか（合否は新しい評価セット v9 で。v9 は、機能にない依頼の形を「操作」と「問い合わせ」で半分ずつにする）
- 語の部分一致を、形態素解析（fugashi）で語単位の一致にするか
- 根拠が無いときに「聞き返す」か「その機能はありません」と返すか
- BERT の役割（いまの「機能にない依頼の例で学習」のままにするか）
