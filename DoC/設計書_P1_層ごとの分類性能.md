# 設計書 ── P1: 層ごとの分類性能（Gemma 4 E2B を何層まで減らせるか）

2026-09-30 ｜ 版 0.2（層を足す・誤りを行ごとに調べる 9 節を追加）｜ 対象: `app/common.py`・`app/p1_extract_layers.py`・`app/p1_heads.py`・`app/p1_compare.py`・`app/p1_errors.py`・`scripts/run_p1.ps1`

## 1. 目的

EdgeSLM_AndroidGemma4Head では、Gemma 4 E2B（35 層）の最後の正規化の出力 `h` から、小さな分類ヘッド（行き先 9・ArgMode 6・棄却）で
車載の発話を分類している。分類だけなら文章を作る力は要らないので、**後ろの層を切っても分類の精度が落ちない**可能性がある
（層を丸ごと外す Layer Pruning。汎用の LLM では 25〜30% 削減の研究例が多いが、用途を分類に絞れば 50% 前後も狙える）。

P1 では、**層を n 個だけ残したモデル（層 0〜n-1＋最後の正規化）の `h`** でヘッドを学習し、n ごとの精度を 35 層と比べる。
重みは学習し直さない（切るだけ＋ヘッドを学習し直す）。**お試しのサンプル**で、既存のプロジェクト・アプリには影響させない（2 節）。

## 2. 既存のものに影響させない

- 新しいプロジェクト `EdgeSLM_AndroidGemma4Prune/` に作る。書き込むのは本プロジェクトの `work/`・`results/` だけ
- ほかのプロジェクトは読むだけ（`DoC/引き継ぎ一覧.md`）。EdgeSLM_MultiHead_Multi の venv も使うだけ（パッケージは入れない）
- 端末・アプリは使わない（PC の GPU だけ）

## 3. 考え方

- 層を n 個残したモデルの出力 ＝ 層 n-1 の出力に**最後の正規化**（`norm`）を掛けたもの。35 層のモデルに 1 回流し、各層の出力をフックで取れば、
  n ごとにモデルを作り直さなくてよい（層は前から順に計算するので、層 0〜n-1 の出力は後ろの層があってもなくても同じ）
- Gemma 4 E2B の作り: 層 15〜34 は層 13（局所）・層 14（全体）の K/V を使い回す。**n=15（層 0〜14）は使い回す層をすべて外す切り目**で、
  端末用のグラフも素直に作れる（K/V の受け渡しが要らない）。n≦15 はどれも同じく作れる
- PLE（層ごとの埋め込み）は層ごとに 256 次元ずつ。n 層なら表も n/35 で済む（端末の表 1,120MB → 15 層で約 480MB）
- ヘッドは今と同じ（edge_router の MultiHead: mlp・linear × seed 3 つ、判定の基準も同じ）。**線形の分類器（linear）も並べる**（どの層の表現が線形に分けやすいか）

## 4. 取り出し（`app/p1_extract_layers.py`）

- モデルの読み方・符号化は EdgeSLM_AndroidGemma4Head の `app/g1_extract.py`（md5 91e29bfc）と同じ（関数を写した）: QAT モバイル版を HF で読み、
  SRQ（活性の 8bit の丸め）あり＝端末と同じ。F2 の文（状態＋履歴なし＋発話）を Gemma 4 のチャットテンプレート（system なし）で包み、1 行ずつ流す
- 35 個の decoder layer にフックを掛け、各層の出力に `norm` を掛けて、最後のトークンと全トークンの平均を取る
- 保存: `work/p1/all_layers.npz`（`last`・`mean` [35, 714, 1536] float32、約 300MB）・`all_layers.meta.json`（層ごとの h の大きさなど）・`token_ids.json`
- 確かめ:
  1. 35 層目＋norm ＝ モデルの `last_hidden_state`（相対L2 1e-5 以下でなければ止める＝フックの場所の確かめ）
  2. 35 層目 ↔ G1 の特徴（EdgeSLM_AndroidGemma4Head `work/g1/srq/features`。同じ設定で以前に取ったもの）の差を記録

## 5. ヘッド（`app/p1_heads.py`）

- 既定の層の数: 4・6・8・10・12・14・**15**・17・20・24・28・35（35 は G1 の再現。ほかは `--layers` で足せる）
- `prepare`: `all_layers.npz` から n の `h` を切り出して `work/p1/L<n>/features/`（edge_router の特徴の形式 `last__last`・`last__mean`）へ
- `train`・`evaluate`・`crossval` を EdgeSLM_AndroidGemma4Head の G1・B4・C3 と同じく**そのまま**呼ぶ（`work/p1/L<n>/heads`・`crossval`）
- 1 つの n で 3 分ほど。作成済みの n は飛ばす（`--force` で作り直す）

## 6. 比べる（`app/p1_compare.py`）

|列|中身|
|---|---|
|交差検証 mlp|5 分割の交差検証の正解率（seed 3 つの平均±標準偏差）|
|35 層との差|n=35 の交差検証 mlp との差|
|交差検証 linear|線形の分類器の正解率|
|全基準・誤実行・棄却の再現率|edge_router の判定の基準（configs/evaluation.yaml）を満たした構成の数、書き込み系の誤実行（S2+S3）、意図が不明の再現率|
|test mlp s7|test の正解率（端末に載せる候補のヘッド）|
|NPU・PLE の目安|改善版 B の 35 層の実測（1 回 88.5ms・PLE の表 1,120MB）を n/35 で割り振った粗い見込み|

まとめとして「35 層との差が 0.01 以内に収まる最小の n」と「一番よい n」を出す。結果は `results/P1/compare_table.md`・`compare.json`。

## 7. 判断の目安（P2 に進むか）

- n=15 以下で 35 層との差が 0.01 以内 → P2（層 0〜n-1 の分類専用グラフを端末で）に進む価値が高い
- 差が大きい → どの層で落ちるか（崖）を記録。学習し直し・蒸留（P3）の検討材料にする（ただし QAT の重みが崩れるので、端末の量子化の作り方から考え直しが要る）

## 9. 誤りを行ごとに調べる（`app/p1_errors.py`、版 0.2）

1 回目の結果（`results/P1_20260929_layer_probe.md`）で、層 17 は正解率が 35 層とほぼ同じ（−0.005）なのに、書き込み系の誤実行（S2）が 2 件出た。
交差検証の報告に残る「誤実行に到達した発話」を見ると、**層 6〜20 の誤実行はほぼすべて同じ 1 文「行く、やめる」**（自己矛盾・正解は意図が不明）
が「ナビの目的地を設定」へ進んだもの（層 12 だけ「案内が丁寧で助かる」も 1 件）。層 24 以上では出ない。

`app/p1_errors.py` は、交差検証の学習済みヘッド（`work/p1/L<n>/crossval/<kind>_seed<s>_fold<k>/`）を読み直し、edge_router の crossval と
同じ手順（fold の分け方・温度・閾値の選び方・判定）で test の判定を作り直す（学習はしない。誤実行の件数が報告と一致するかも確かめる）。

1. 誤実行に到達した行: 確信度と TOOL_write の閾値、棄却の得点と REJECT の閾値 → **どちらの閾値をどれだけ動かせば止まったか**
2. 過剰な聞き返しの多い発話
3. 閾値の感度: REJECT を下げる（≤0.9・0.8・0.5）× TOOL_write を上げる（≥0.7・0.8・0.9）の 16 通りで、誤実行・正解率・過剰な聞き返し・棄却の再現率。
   **test を見て閾値を動かすので楽観的**な目安（閾値で消せる種類の誤りかを見るため。閾値の選び直しではない）

層を足す（16・18・19・25・26・27）のは 17 と 28 の周りの形を細かく見るため（`app/p1_heads.py` の `--layers`）。

```powershell
.\scripts\run_p1.ps1 -Layers "16,18,19,25,26,27" -Errors -ErrorLayers "17,24,28,35"   # 20 分＋12 分ほど
```
